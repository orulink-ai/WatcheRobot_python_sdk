# 音频发送窗口与设备接收确认

Application transport 和 Desktop session 共用 `AudioInFlightWindow`。设备的
`evt.audio.buffer_status` 是队列状态快照，并不是每次都新增一批发送额度。

设备上报的 `expected_rx_seq` 表示下一期待接收的音频包序号。发送前先记录已预留包数，
再从快照推导的额度中扣除 `已预留包数 - expected_rx_seq`。这样重复状态不会将仍在
Daemon、TCP 或设备接收链路中的包重新当成空闲容量。窗口只保存计数，不额外缓存音频。

- 每次新流重置计数，保留原有四包启动额度；v1最多八包补充额度，continuous最多32包补充额度，均受目标pending槽数、free_frames和接收水位的在途扣减限制。
- 设备队列容量仍按每包占用的 PCM 槽数计算；接收确认以 WSPK 包为单位。
- 回退、负数、布尔值及超出已发送范围的确认不更新额度。
- 旧固件不带接收序号时保留原有流控；同一流一旦收到有效序号，不再退回旧算法。
- 不改变 Daemon 透明转发，不调整命令超时或扩大设备音频队列。

回归测试使用两个真实发送循环，验证启动、重复状态、接收推进和无效确认的实际发包数。
这项修复限制在途积压，不能保证弱网下永不超时，也不替代设备端发送重试和资源回收。

连续PCM写入与跨write分帧见[连续播放合同](continuous-audio.md)。设备队列大小和起播阈值不因连续API改变；小PCM写入在SDK聚合为4096字节帧，避免占满槽位却不满足字节预缓冲。
