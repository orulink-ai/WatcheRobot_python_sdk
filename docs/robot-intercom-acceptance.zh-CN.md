## 0.1.2：拍照预计倒计时与重复实机验收

用户反馈点击拍照后等待较久、缺少即时反馈。通过 Application 现有拍照接口
测量三张照片，请求、传回及本机保存分别耗时 1875 / 1937 / 1812 ms；同一
照片的本机 HTTP 读取仅 0 / 16 / 0 ms。串口显示 PTL 相机预热约 1.21 秒，
等待 12 个有效帧并丢弃 3 个快门前旧帧，之后再取新帧、复制、传回和收尾。
固件预热用于模式切换后的曝光稳定，防止第一张图发黑。本次没有修改固件
预热策略，也没有人为延迟拍照请求。

新增独立拍照控制器：点击立即请求并显示预计 2 秒倒计时，按成功操作的实际
耗时调整后续估计。超过估计仍显示等待时长；收到元数据后进入图片加载阶段，
图片解码成功才显示完成。禁止重复点击，15 秒超时中止本机请求并允许重试，
失败保留旧照片，页面退出取消计时器与请求，过期结果不能覆盖新照片。
倒计时不是精确快门时刻，拍照与 RTC 保活仍相互独立。

同一天使用 Codex 内置浏览器、真实电脑麦克风、电脑扬声器和实体机器人，

用户报告页面出现 `WebRTC disconnect recovery timed out`。历史故障发生时没有
完整的设备停止原因与浏览器状态时序，不能证明下述复现是该截图的唯一原因。

代码核对发现固件 RTC 保活期限为 5 秒，而初版由浏览器 JavaScript 定时器
发送保活。设备启动后暂停页面主线程 6.5 秒，实际设备产生
`stopping / stopped`，停止原因为 `heartbeat_timeout`，恢复页面后回到 idle。
这证实页面计时器暂停足以导致设备主动断开，即使设备和局域网仍然在线。

修复将设备保活交给 Application 后端，每秒通过原注入的 RTC channel 发送。
本机页面 WebSocket 的原生 ping/pong 独立判断页面连接仍存在，避免把暂停
定时器当作退出；关闭页面或浏览器异常退出仍释放通话。拍照不持有信令锁，
旧页面与旧配对无法控制新通话。没有新增设备业务连接，也没有改变 Daemon
业务路由或固件 RTC 超时常量。HTTP 端口在本机保存并在重启时复用，减少
浏览器因 origin 变化重新等待麦克风权限的问题。

补充有界诊断窗口和 Application 日志，记录 peer/ICE、页面可见性、音频包
进度、设备状态与停止原因；不记录 SDP、音频、照片或现场内容。页面正常
退出标记为 `page_closed`，避免误记为用户点击结束。

修复前后实体设备对照验证：

| 场景 | 初版 | 修复后 |
| --- | --- | --- |
| 暂停页面 JavaScript 6.5 秒 | 设备 `heartbeat_timeout`，恢复后 idle | 全程 connected，恢复后 running |

使用注入的语音 WAV，媒体经过实体机器人。修复后未记录页面异常或非预期

## 0.1.0 初版记录

### 功能与架构

从 SDK Test Bench 抽离局域网双向原声通话、实际播放 PCM 驱动的程序嘴型、
按钮拍照及本机保存。网页资源和 RNNoise 依赖随包分发，运行时不依赖测试台
目录或外部 CDN。Application 使用 Daemon 注入的 Device channel；没有新增
设备业务连接，也没有修改 Daemon 的业务路由。

每个页面持有独立通话请求标识。启动失败、丢失确认、停止重试、拍照与心跳
并发、浏览器退出及设备配对变化都有回归覆盖。设备可能复用通用 device ID，
因此清理在发送前核对原配对会话。该检查不等于原子绑定发送；SDK 当前 Device
channel 仍使用当前设备连接，检查后立即切换配对存在竞态。通话或释放期间切换
设备不受支持，需先结束通话再操作配对，不能宣称完全隔离并发设备切换。
