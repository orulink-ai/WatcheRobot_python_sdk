# 机器人对讲验证与分发记录

验证日期：2026-10-12。应用源码位于 `examples/robot_intercom`，身份为
`com.orulink.robot_intercom`，使用 SDK 0.1.11 的受管 Application 运行时。

## 0.1.1：RTC 自动断开调查与修复

用户报告页面出现 `WebRTC disconnect recovery timed out`。历史故障发生时没有
完整的设备停止原因与浏览器状态时序，不能证明下述复现是该截图的唯一原因。

代码核对发现固件 RTC 保活期限为 5 秒，而初版由浏览器 JavaScript 定时器
发送保活。设备启动后暂停页面主线程 6.5 秒，实际设备产生
`stopping / stopped`，停止原因为 `heartbeat_timeout`，恢复页面后回到 idle。
这证实页面计时器暂停足以导致设备主动断开，即使设备和局域网仍然在线。

修复将设备保活交给 Application 后端，每秒通过原注入的 RTC channel 发送。
本机页面 WebSocket 的原生 ping/pong 独立判断页面连接仍存在，避免把暂停
定时器当作退出；关闭页面或浏览器异常退出仍释放通话。拍照不持有信令锁，
旧页面与旧配对无法控制新通话。没有新增设备业务连接，也没有改变 Daemon
业务路由或固件 RTC 超时常量。HTTP 端口在本机保存并在重启时复用，减少
浏览器因 origin 变化重新等待麦克风权限的问题。

补充有界诊断窗口和 Application 日志，记录 peer/ICE、页面可见性、音频包
进度、设备状态与停止原因；不记录 SDP、音频、照片或现场内容。页面正常
退出标记为 `page_closed`，避免误记为用户点击结束。

修复前后实体设备对照验证：

| 场景 | 初版 | 修复后 |
| --- | --- | --- |
| 暂停页面 JavaScript 6.5 秒 | 设备 `heartbeat_timeout`，恢复后 idle | 全程 connected，恢复后 running |
| 暂停页面 JavaScript 25 秒 | 未追加重复故障测试 | 全程 connected，恢复后 running |

上述对照使用 Chromium 的 Debugger 暂停，而非只切换页面可见性；活跃媒体
页面的 lifecycle frozen 命令未实际暂停定时器，不能当作有效复现。测试麦克风
使用注入的语音 WAV，媒体经过实体机器人。修复后未记录页面异常或非预期
设备终止事件。下方保留初版验收记录，避免混淆版本与测试输入。

0.1.1 的 Python 服务与 SDK RTC 回归共 42 项通过（独立应用 23 项）；浏览器
控制器和采集、延迟、恢复、降噪模块共 35 项通过。新增行为先验证失败，再
实现修复。`watcherobot app check examples/robot_intercom`、Python 编译检查、
JavaScript 格式化和 Git 空白检查通过。

追加 Codex 内置浏览器、真实电脑麦克风、电脑扬声器和实体机器人的连续
600 秒通话测试：586 次状态采样全部为 running / connected，设备终止原因
始终为空。电脑扬声器分别在第 5、45、90 秒播放语音，另在隐藏页面期间
播放一次，机器人实际播放嘴型幅度达到 739/1000，发声帧增加 90，表情更新
错误为 0。通话中拍照得到 640 × 480 JPEG；静音、恢复麦克风、关闭与恢复
现场收听、隐藏与恢复页面均成功。

观察窗口内设备发送音频包增加 29,939，解码帧增加 29,917；发送错误、渲染
错误、上行丢帧、播放队列丢帧均为 0，浏览器诊断采样的丢包为 0。正常结束
后 release.complete=true、failures=[]，RTC、媒体系统、程序嘴型、画布、
缓存和 LCD DMA 均释放为零。原始时序、截图和串口日志仅保存在本机。

本次验证有两个明确边界：扬声器靠近机器人时，设备麦克风削顶计数增加
5,247，AEC reference-starved 计数增加 251；通话期间内部内存约 17.6 KB，
最大连续块 8.7 KB，固件内存监控仍报告 critical。观察到的连接没有因此
断开，不能据此认定这些指标无风险，也不能用包计数替代主观听感及 LCD
视觉验收。本次解决的是已复现的页面定时器保活超时路径。

加载最终网页后，真实麦克风重连与正常结束成功；另开页面建立实体通话，
直接关闭该页面后自动回到 idle，退出原因为 page_closed，RTC 和嘴型均关闭、
release.complete=true。两次停止后的内部可用内存分别为 44,834 / 44,818
字节，DMA 为 37,142 / 37,126 字节；这是有限次数验收，不据此宣称长期无泄漏。
重启独立 Application 后仍复用原本机 origin，设备连接保持，应用处于 idle，
没有继续占用麦克风。

## 0.1.0 初版记录

### 功能与架构

从 SDK Test Bench 抽离局域网双向原声通话、实际播放 PCM 驱动的程序嘴型、
按钮拍照及本机保存。网页资源和 RNNoise 依赖随包分发，运行时不依赖测试台
目录或外部 CDN。Application 使用 Daemon 注入的 Device channel；没有新增
设备业务连接，也没有修改 Daemon 的业务路由。

每个页面持有独立通话请求标识。启动失败、丢失确认、停止重试、拍照与心跳
并发、浏览器退出及设备配对变化都有回归覆盖。设备可能复用通用 device ID，
因此清理同样绑定原配对会话，不能向新配对发送旧通话的控制帧。

### 自动验证

先建立失败测试，再实现服务与浏览器生命周期；实机配对后发现的能力刷新和
配对会话隔离问题也分别补充了失败测试。

- Python 服务与 SDK RTC 测试：33 项通过，其中独立应用服务测试 14 项。
- 浏览器控制器与复用的采集、恢复、降噪模块测试：21 项通过。
- `watcherobot app check examples/robot_intercom` 通过。
- 桌面与窄屏页面检查通过；实机浏览器测试未记录页面异常。

复用媒体模块与测试台版本逐文件比较一致。发布包包含各模块及第三方许可证。
本次新增代码没有可直接执行的系统脚本；验收脚本及原始设备日志保留在本机，
不进入 Git 或应用发布包。

### 真实设备验证

使用 ESP32-S3 实体机器人、PTL 相机、同一局域网、启用 debug 的 NoWake 固件。
通过 debug 打开 `sdk.control.app` 并完成 SDK 配对，未修改固件业务源码。
固件版本为 v0.4.5，报告 commit `67aee88884b0`，dirty=false；应用分区 SHA-256：

```text
65E56DB6DB21FE1AE1B0E78ACAACBA192A4CD871381E8487F5931189DE83990B
```

浏览器以语音 WAV 注入麦克风，音频实际经过 WebRTC 到实体机器人；回传音频、
播放 PCM、嘴型及相机由实体设备提供。此次验证属于链路与资源验收，未完成
真人麦克风、主观听感或现场 LCD 视觉验收。

约 30 秒通话采样和 3 次拍照的结果：

| 项目 | 结果 |
| --- | --- |
| 浏览器发送 / 接收音频包 | 采样最大值 1704 / 1700 |
| 设备解码音频帧 | 停止前统计 1762 |
| 实际播放嘴型幅度 | 0–982 / 1000 |
| 程序表情刷新率 | 采样平均约 19.8 FPS，目标 20 FPS |
| 音频发送 / 渲染错误 | 均为 0 |
| 上行丢帧 | 0 |
| 播放队列丢帧 | 1；尚不能宣称零丢帧 |
| 拍照 | 3 张 JPEG，均为 640 × 480，6177 / 6173 / 6186 字节 |
| 静音及重新开始 | 按钮切换正常，另两轮开始 / 停止成功 |
| 停止释放 | release.complete=true，failures=[] |
| 停止后画布、缓存与 LCD DMA | 均为 0，RTC 与媒体系统停止 |

另外连续执行 10 轮开始 / 停止，每轮停止后内部可用内存均为 44,974 字节，
DMA 可用内存均为 37,282 字节，未出现逐轮下降。关闭活跃浏览器后服务自动
回到 idle，释放完成且无失败。配对保护收紧后重新加载应用并进行最终冒烟检查。

原始 JSON、截图、照片及音频不提交，避免发布本机信息和现场内容。
