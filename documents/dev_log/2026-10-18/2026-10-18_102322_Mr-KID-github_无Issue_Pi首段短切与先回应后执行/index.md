# Pi 首段短切与先回应后执行

- 创建：2026-10-18 10:23:22 Asia/Shanghai；建档作者：Mr-KID-github；实施：Codex/root、tts_first_segment、pi_latency_plan。
- 状态：本地实现、215项回归及两轮真实播放验证完成，已恢复并部署本机正式Application；未提交、未推送。
- 用户要求：推进首段短切、后续预取；每次收到用户消息先回复，再执行后续操作。

## 目标与边界
- 最终回复首段约28字符，在自然停顿切开，后续约80字符，保留完整Unicode/字节边界和按序预取。
- 识别完成并关麦后，先播本地固定确认语“收到，我来处理。”，播放确认完成后才提交Pi业务prompt；缓存确认语音频减少后续等待，最终结果仍等agent_settled。
- 确认语只说明已收到，不虚构手机任务完成；页面将Application确认与Pi最终回复区分。暂停/确认播放失败不得继续触发Pi操作。
- 保留ASR持续采音解耦、真实错误诊断、半双工、音频/动作所有权和Daemon内容无关路由。不改固件协议，不声称同一句PCM边到边播。

## 调查与方案
现实现按句末/换行及80字符切分，第一段必须全合成完成才能下发。实际日志一轮首包353ms、整段4855ms，表明首段过长仍增加首次播放等待。已有容量一的后续合成队列与跨轮HTTP连接池，继续复用。

固定确认语的内存缓存只保留一条，按当前TTS配置（含音色/资源/凭据）和文本识别，不落盘；取消/失败不能存入或晚播。模型可提前启动进程，但实际ask及其工具操作必须排在确认语播放完成后。

## 验收
首段/自然停顿/URL与数字/UTF8全文无丢失；确认完成→Pi开始顺序；确认失败及暂停零Pi任务；跨轮缓存和配置失效；原ASR/行为回归；真实设备验证、恢复正式应用。
